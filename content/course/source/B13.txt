~m
FastAPI is the standard Python web framework for wrapping AI logic and agents behind clean HTTP endpoints. Check the current details for recent FastAPI releases.

Unlike ordinary database endpoints that return a tiny JSON object in twenty milliseconds, an LLM call generates tokens over several seconds. FastAPI supports **Server-Sent Events (SSE)** and streaming responses out of the box, letting your server yield each token or agent status event to the browser the instant it arrives from the model provider.

+ It sends tokens and status updates to the user's screen as they are generated, rather than making the user stare at a blank screen for seconds
- It makes the model generate fewer tokens overall
- It allows FastAPI to run without Python installed
- It encrypts the database schema
= Streaming starts displaying output within a second, making a multi-second model call feel responsive.
## Async processing and queues
A single AI worker spends most of its time waiting: waiting for the model API to reply, waiting for a vector search, or waiting for a third-party webhook.

If your web server handles requests synchronously, one slow ten-second agent call blocks that worker thread from serving anyone else. Using `async`/`await` in Python or TypeScript lets a single server handle dozens of concurrent waits efficiently. For heavier background jobs, a **task queue** (such as Celery, BullMQ, Redis queues or cloud queues) holds incoming jobs safely and feeds them to worker processes at a controlled pace.

It is a busy deli counter handing out numbered tickets so the server does not freeze when twenty customers walk in at once.
?? What are the roles of `async`/`await` and task queues in an AI backend?
+ Async code handles many concurrent network waits without blocking threads, while task queues buffer and distribute heavier background jobs safely
- They make language models run without an internet connection
- Task queues delete any request that takes more than one millisecond
- Async code is only used for styling buttons in CSS
= Non-blocking async I/O and durable task queues keep your web server responsive when many users trigger slow model calls at once.
## Long jobs run in the background, not inside a web request
Standard web requests, load balancers and serverless functions impose strict timeouts, often between 30 and 120 seconds. A deep research agent, a batch contract review or a multi-step workflow can easily take three minutes.

Never run a multi-minute agent loop directly inside the HTTP request that the user's browser is waiting on. Instead, have the `POST /jobs` endpoint validate the input, write a job row to the database, push the job ID onto a background worker queue and immediately return `202 Accepted` with the `job_id`. The frontend then polls or subscribes to updates for that ID.

It is dropping your suit at the dry cleaner's and taking a claim ticket, rather than standing at the counter while it washes and dries.
?? How should an API handle an agent task that takes three minutes to complete?
+ Enqueue the job for a background worker, return a job ID immediately and let the client track progress asynchronously
- Hold the initial HTTP request open for three minutes and hope the load balancer does not cut the connection
- Refuse any task that takes longer than two seconds
- Ask the user to refresh the page every second
= Decoupling long agent runs into background jobs prevents HTTP timeouts and lets runs survive browser refreshes.
## Login and per-user data separation
The moment your prototype moves from your laptop to real users, authentication and tenant isolation become non-negotiable.

Every API request must verify who the user is via a signed session cookie or token, and resolve their `user_id` and `organisation_id` on the server. Pass those verified IDs directly into every database query, vector search filter and tool call in code. Never let the language model choose which `organisation_id` to query based on a prompt, or one user will be able to ask for another client's confidential files.

It is a bank cash machine checking your card and PIN before showing only your own account balance.
?? How must per-user and per-client data separation be enforced in an AI application?
+ By filtering every database query, vector search and tool call in server code using the authenticated session's user and organisation IDs
- By asking the model nicely in the system prompt only to read the current user's rows
- By putting every client's documents into one unfiltered vector collection
- By letting the user type their `organisation_id` into the chat box
= Enforcing tenant filters in backend code from the authenticated session makes cross-client data leaks impossible via prompt tricks.

## Environment variables and secrets kept outside the image
Never hard-code API keys (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, database passwords) in your source code or bake them into a Docker image with `COPY .env`.

Anyone who pulls that image or reads its layer history can extract your secret keys in seconds. Instead, build the image with code only, and inject configuration and secrets at **runtime** through environment variables supplied by your cloud secret manager (such as AWS Secrets Manager, Google Secret Manager or Azure Key Vault). Add `.env` to both `.gitignore` and `.dockerignore`.

It is building a safe with the combination set at installation by the owner, rather than painting the code on the door at the factory.
?? How should API keys and database passwords be passed to a containerised AI service?
+ Injected at runtime via environment variables from a secret manager, never baked into the Docker image or committed to Git
- Written directly at the top of `main.py` so they are easy to find
- Copied into the Docker image during `docker build` and pushed to Docker Hub
- Sent in the URL query string of every user request
= Keeping secrets in runtime environment variables prevents leaks through Git repositories or container registries and lets you rotate keys without rebuilding.
## The same container in testing and production
In a healthy deployment pipeline, you build the Docker image once from a specific Git commit hash (for example, `myapp:3ab783c`), run your automated unit and evaluation tests against that exact image in staging, and then promote that **exact same image** to production by changing only its environment variables.

It is testing a batch of medicine in the lab and shipping bottles from that exact tested batch, not mixing a new batch on the lorry.

- Because building an image twice costs a million pounds
- Because production servers cannot run `pip install`
- So that test database data is copied to real customers
= Pinning dependencies in lockfiles and promoting the tested image artifact guarantees that production matches what passed staging.

## API rate limiting
Every model provider enforces **rate limits** on your account, typically measured in **RPM** (requests per minute), **TPM** (tokens per minute) and sometimes **TPD** (tokens per day).

If a sudden burst of users or a parallel batch script exceeds your TPM limit, the provider returns HTTP `429 Too Many Requests`. Your code should handle `429` responses gracefully by reading the `Retry-After` header (if provided) and waiting with **exponential backoff plus random jitter** (for example, wait 1s, then 2s, then 4s, plus a few hundred random milliseconds so twenty waiting requests do not all retry at the exact same instant).

It is motorway slip-road traffic lights that space cars out one by one so the main carriageway does not jam solid.
?? Why should retry logic add random jitter to exponential backoff when handling `429` rate-limit errors?
+ So multiple requests that were rate-limited at the same moment do not all retry at the exact same second and trigger another `429` spike
- Because providers require a random number in every prompt body
- To make failed requests fail immediately without waiting
- Because jitter reduces the number of tokens in a sentence
= Exponential backoff with jitter spreads out retries smoothly instead of hammering the API in synchronised waves.
## Quotas and backpressure
Retries help with brief two-second spikes, but if ten thousand items flood in while your provider quota only allows a hundred per minute, retrying inside the web server will just pile up thousands of waiting connections until your server runs out of memory.

You need **quotas and backpressure**. Limit concurrency with a semaphore or token-bucket rate limiter before requests ever hit the provider. When the queue is full, apply backpressure: slow down the ingestion job, queue requests neatly with an estimated wait time, or shed low-priority background work first so live interactive users still get served.

It is a nightclub bouncer holding the queue outside behind a rope when the room inside reaches safe capacity.
?? What is backpressure, and why is it needed alongside simple retries?
+ Controlling incoming concurrency and queuing or slowing new work when downstream capacity is full, preventing retries from overwhelming your server
- Calling the API ten times faster whenever a `429` error occurs
- Turning off all rate limits on the database
- Deleting the user's account if they type too fast
= Backpressure protects your own system and prioritises live user traffic when demand exceeds downstream API quotas.
## Per-user and per-client budgets
Even if your overall company API quota is huge, a single runaway script, an enthusiastic power user or a malicious bot can burn through your entire monthly budget in an afternoon if there are no per-user limits.

Enforce rate limits and token budgets at the **user** and **client tenant** level in your own application database or Redis cache. For example, allow a standard user 30 messages per hour and £2 of token spend per day, and give each client organisation a monthly token allowance tied to their subscription tier, with an alert at 80% usage.

It is a hotel buffet putting out sensible plates rather than letting the first guest tip the entire tray of bacon into a rucksack.
?? Why do you need per-user and per-client token budgets in your own app even when your provider tier has high limits?
+ To stop a single heavy user, bug or script from consuming the entire shared budget or starving other customers of quota
- Because providers automatically bill each of your end users' personal credit cards
- To make sure nobody can use the app more than once a year
- Because databases cannot count tokens per user
= Per-user and per-tenant caps protect your margins and prevent one noisy neighbour from degrading the service for everyone else.

Sooner or later, a user will hit their daily cap or a provider outage will exhaust your fallbacks. How your app behaves in that moment defines whether the user stays calm or loses trust.

## Prompt, model, and config versioning
In an AI system, your prompts, model identifier, temperature, tool schemas and guardrail thresholds change behaviour just as much as your Python or TypeScript code does.

Treat all of them as **versioned artefacts**. Keep prompts and configurations in Git (or a versioned prompt registry linked to commits) rather than editing live strings in an untracked database table. Every change should have a version identifier, an author, a commit message explaining why it changed, and a link to the evaluation run that approved it.

It is a commercial bakery keeping numbered recipe cards in a binder so everyone knows what changed between Recipe v4 and Recipe v5.
?? Why should prompts, model identifiers and tool schemas be kept under version control just like application code?
+ Because changes to any of them alter system behaviour, and version history lets you review diffs, run CI evals and roll back cleanly
- Because models run faster when prompts are stored in Git
- So that nobody on the team can see what the system prompt says
- Because databases cannot store strings longer than ten characters
= Versioning the whole AI configuration bundle (prompt + model + parameters + tools) makes every change auditable and reversible.
## Data versioning for RAG indexes
When a RAG answer changes from one week to the next, the culprit is often not the prompt or the model; it is the **retrieval index**. New PDFs were ingested, a chunking script was changed from 500 to 800 tokens, or the embedding model was upgraded.

Version your RAG index alongside your code. Record which source documents (with file hashes and timestamps), which chunking parameters and which embedding model built `index_v2026_11_13`. Build new indexes under a new versioned collection or alias (`kb_v4`), run your retrieval and RAG evals against `kb_v4`, and flip the live alias from `kb_v3` to `kb_v4` only when the scores pass.

It is printing a new edition of a reference textbook and checking the index before replacing the copies in the library.
?? Why is building a new RAG index under a versioned alias (`kb_v4`) better than overwriting chunks in place inside the live index?
+ You can test the new index on your eval suite before switching traffic, and switch back to `kb_v3` instantly if a problem appears
- Overwriting in place is the only way to keep a backup
- Vector databases only allow one collection to exist on a server
- Embedding models never change their vector dimensions
= Blue-green index aliases give you safe testing before cutover and an instant rollback if a chunking or ingestion change hurts retrieval.
## Pinning model versions: providers update and retire models
~m
In API calls, model names come in two styles: a floating alias (such as `gpt-4o` or `claude-sonnet-4`) and a **pinned dated snapshot** (such as a specific version string or release snapshot). Check the current details in your provider's model documentation.

If you use a floating alias in production, the day the provider points that alias to a newer snapshot, your production behaviour changes overnight without a single commit in your repository. Always pin the exact snapshot identifier in production configs, test new snapshots on your eval suite in staging first, and upgrade on your own schedule.

- Providers never update floating aliases
- Pinned snapshots do not require an API key

## Eval-gated deployments
In standard CI/CD, a deployment pipeline blocks a release if a unit test or type check fails. In **LLMOps**, you add an **eval gate** to that same pipeline.

Before a new prompt, tool or model version can deploy to production, the pipeline automatically runs your evaluation suite against the candidate build and compares the scores against your minimum thresholds (for example: faithfulness >= 95%, safety pass rate = 100%, p95 latency <= 6s, cost per task <= £0.04). If any gate fails, the deployment stops automatically and posts the failing test cases on the pull request.

It is an automated passport gate at the airport that only opens the barrier when every check on the chip passes.
?? What is an eval-gated deployment in LLMOps?
+ An automated deployment pipeline that blocks a release if the candidate version fails accuracy, safety, latency or cost thresholds on the eval suite
- A manual meeting where managers guess whether a prompt sounds nice
- Deploying straight to production and running tests a month later
- Blocking all deployments on Tuesdays
= Making eval thresholds an automated gate in CI/CD stops regressions from reaching production users.
## Rollbacks and canary releases
Even with good offline evals, real production traffic can hit an unexpected snag. Two deployment habits make releases low-stress: **canary releases** and **instant rollbacks**.

A **canary release** routes a tiny slice of live traffic (say 2% or internal staff accounts first) to the new version while watching error rates, latency, guardrails and user feedback. If everything stays green for an hour, traffic ramps to 25% and then 100%. If anything spikes, an **instant rollback** flips traffic back to the previous known-good container, prompt version and index alias in seconds.

It is dipping a toe in the bathwater before jumping in, with the cold tap right in reach.
?? How do canary releases and instant rollbacks reduce deployment risk?
+ A canary exposes only a small slice of traffic to a new version first, and a rollback switches back to the previous working version immediately if metrics degrade
- Canary releases send the new version to 100% of users with no monitoring
- Rollbacks require rewriting all the code from scratch while users wait
- They remove the need for any logging or alerts
= Gradual traffic ramping plus one-click rollback limits the blast radius of any surprise production issue to a tiny fraction of requests.
## Feature flags to switch behaviour without redeploying
Waiting ten minutes for a full container rebuild and cloud deployment when a provider is having a bad afternoon or a new prompt is misbehaving feels like an eternity.

Put key AI switches behind **runtime feature flags** (or a hot-reloaded configuration table) that you can flip in two seconds without redeploying code: which model and provider a route uses, which prompt version is active, whether a new agent tool is enabled, and what the maximum step cap is. Include a global **kill switch** that cleanly disables an autonomous feature and falls back to human queueing if an emergency occurs.

It is a circuit breaker panel on the wall: you can flip one switch off in a second without calling an electrician to rewire the house.
?? Why should model selection, prompt versions and autonomous actions be controlled by runtime feature flags?
+ So you can switch models, roll back a prompt or disable a misbehaving tool in seconds without waiting for a full code redeploy
- Because feature flags make Python code run without a server
- So end users can edit the company's database schema
- Because redeploying a container takes half a millisecond
= Runtime flags and kill switches give operations teams instant control during model outages or unexpected agent behaviour.
## Planning for model retirement and migration
Every pinned model snapshot you use today will eventually be retired by its provider, often with three to six months' notice. If your prompts and code are brittle and you have no eval suite, every model retirement becomes an unscheduled crisis.

Turn model migration into a routine, calm two-hour chore. Keep a central inventory of which pinned model versions are used where and their announced deprecation dates. When a replacement snapshot arrives, point a branch at the new model ID, run your offline eval suite, adjust any prompt phrasing where the new model behaves differently, run shadow or canary traffic for a few days, and flip the flag well before the deadline.

It is renewing your passport a month before it expires rather than discovering it is out of date at the airport check-in desk.
?? What makes migrating to a new model before a provider retirement deadline quick and low-risk?
+ Having model IDs centralised in config and an automated evaluation suite ready to verify and tune prompts against the replacement model
- Waiting until the day after the old model is turned off to see what breaks
- Hard-coding the old model name in fifty separate files with no tests
- Refusing to ever upgrade models
= Centralised model config plus a solid eval suite turns inevitable model retirements into a routine test-and-switch exercise.
