## Choosing workflow vs. agent vs. multi-agent
Choosing between a fixed workflow, a single agent, and a multi-agent system is the foundational architectural decision in any AI project. A deterministic workflow follows a fixed sequence of code steps with model calls at specific points, a single agent decides its own next steps and tool calls in a loop, and a multi-agent system divides complex work across distinct specialist agents.

It is like choosing between a factory conveyor belt for identical parcels, a skilled craftsperson handling custom repairs at one bench, or a full film crew with separate lighting, sound, and camera teams.

Always start with the simplest pattern that solves the client's problem, because every jump up in autonomy adds latency, token cost, and harder debugging.

?? When should an AI architect choose a fixed workflow over an autonomous agent?
+ When the sequence of steps is predictable and known in advance, requiring reliable, low-cost execution
- When the task is completely open-ended and requires inventing a new plan for every request
- When the client wants to spend as many tokens as possible on every API call
- When the engineering team does not know how to write basic conditional statements in code
= Fixed workflows excel when the process steps are well-defined and predictable, delivering lower cost, lower latency, and much higher predictability than open-ended agent loops.

## State, memory, and tool boundaries
State, memory, and tool boundaries define what an agent knows right now, what it remembers across sessions, and what external actions it is permitted to execute. Working state tracks the current task's step-by-step progress, long-term memory stores durable user facts or past lessons, and tool boundaries enforce strict schemas and permissions on every software integration.

Think of a doctor's consultation: the clipboard on the desk holds today's examination state, the patient's medical file is long-term memory, and the prescription pad has strict rules on what drugs can be ordered.

Blurring these boundaries leads to bloated context windows, stale memories polluting new tasks, or agents calling dangerous tools with malformed parameters.

?? How does working state differ from long-term memory in an agent architecture?
+ Working state tracks the progress and variables of the current task, while long-term memory stores facts that persist across separate sessions
- Working state is stored on paper, while long-term memory is stored only inside GPU registers
- Working state is shared publicly with all internet users, while long-term memory is deleted after every token
- Working state controls the user interface font size, while long-term memory controls network bandwidth
= Working state holds the short-term scratchpad, tool outputs, and step status for the active run, whereas long-term memory retains durable knowledge across days or months.

## Start from the task and its risks, not from a framework
Starting from the task and its risks means mapping the client's real business workflow, data sensitivity, latency budget, and failure consequences before picking any orchestration library or agent framework. Many weak projects fail because developers fall in love with a trendy multi-agent library first and try to force a simple business problem into its abstractions.

It is like an architect surveying the soil, local weather, and family needs before deciding whether to build a brick cottage or a steel skyscraper.

Once you understand the task and its risk profile clearly, you often find that fifty lines of plain code and structured API calls beat a heavy framework.

?? Why is it a mistake to choose an agent software framework before analysing the client's task and risks?
+ You may introduce unnecessary complexity, latency, and opaque abstractions for a problem that simple code and workflow steps could solve cleanly
- Agent frameworks are illegal to install before signing a cloud hosting contract
- Frameworks prevent language models from generating text in British English
- Choosing a framework first automatically deletes the client's existing databases
= Designing from the task and its risks ensures your architecture matches real business constraints around latency, cost, and safety rather than forcing the problem into an over-complicated tool.

## What must be exact code and what can be model judgment
Separating exact code from model judgement means deciding which parts of a workflow require 100 per cent deterministic rules and which parts benefit from flexible language understanding. Calculations, permission checks, tax rates, schema validation, and database writes belong in deterministic code, while classifying messy emails, summarising reports, and drafting replies belong in the language model.

If a client's billing assistant calculates VAT and invoice totals inside a language model prompt instead of a coded calculator function, a single rounding hallucination can corrupt the company's financial ledger.

Even the strongest frontier model should never replace an `if` statement or a maths formula when the business rule is exact and unambiguous.

?? Which of the following tasks should always be handled by deterministic code rather than language model judgement?
+ Enforcing user access permissions and calculating exact financial totals or tax rates
- Summarising the tone and main themes of a long, unstructured customer complaint email
- Drafting three creative subject-line options for a seasonal marketing newsletter
- Translating a conversational support reply from English into conversational French
= Exact rules, access control checks, and mathematical calculations require 100 per cent determinism in code, whereas nuanced language interpretation and drafting suit an LLM.

## Designing for failure: what happens when a step goes wrong
Designing for failure means planning explicitly for what your system will do when an API times out, a tool returns an error, a model outputs invalid JSON, or an agent gets stuck in a loop. Production architectures wrap every external call with bounded retries, clear timeout limits, loop counters, and a graceful fallback path to a simpler model or a human queue.

It is like a modern lift that does not simply plummet when a cable sensor trips, but engages mechanical brakes, switches to backup battery lighting, and rings the building engineer.

Without hard step limits and fallbacks, a single broken third-party API can cause an autonomous agent to burn £500 in retry tokens overnight while achieving nothing.

?? What is an essential safeguard when designing an agent loop to handle tool or API failures gracefully?
+ Setting a strict maximum step and retry limit along with a clean fallback path to a human operator or safe error state
- Instructing the agent to retry failed API calls infinitely until the server responds
- Hiding all tool errors from the engineering logs so the dashboard always looks green
- Automatically doubling the model's context window every time a network timeout occurs
= Bounded retries, maximum step counts, and graceful escalation prevent infinite token-burning loops and ensure users get a safe fallback when dependencies fail.

## Writing rigorous specs for coding agents
Writing rigorous specifications for coding agents is the practice of translating a vague feature idea into a structured, unambiguous document before asking an AI coding tool to write a single line of code. Because coding agents move fast and take instructions literally, a fuzzy one-line prompt usually produces sprawling code that misses edge cases and breaks existing patterns.

It is like giving a kitchen builder detailed architectural drawings with exact pipe measurements and cabinet materials rather than waving at an empty room and asking for a nice kitchen.

Spending twenty minutes writing and reviewing a clear spec with your client or engineering lead saves hours of untangling subtle bugs in generated pull requests.

?? Why does spec-driven development dramatically improve results when working with AI coding agents?
+ It resolves ambiguities and defines exact boundaries upfront so the coding agent does not have to guess architecture or edge-case behaviour
- Coding agents are technically unable to generate code unless the input file exceeds five thousand words
- Writing a specification automatically compiles the document into machine code without using an LLM
- Specifications allow the coding agent to bypass all company security and code review rules
= Coding agents amplify both clarity and ambiguity; a rigorous specification removes guesswork around interfaces, edge cases, and constraints before code generation starts.

## Specs as contracts
Treating specifications as contracts means using the written spec as the shared source of truth between business stakeholders, human engineers, and coding agents. Just as a legal contract defines what each party promises to deliver and what counts as a breach, a software spec defines exact data schemas, API signatures, error codes, and invariants that the implementation must honour.

When two separate coding agents build a front-end dashboard and a back-end API simultaneously, a shared API contract ensures their code connects cleanly on the first try.

If requirements change mid-project, you update the specification contract first and regenerate or adjust the code from the updated spec rather than patching files ad hoc.

?? How does treating a specification as a contract help when multiple engineers or coding agents work on different parts of a system?
+ It locks down shared interfaces, data schemas, and behaviours so independent components fit together reliably
- It legally transfers copyright ownership of the software to the cloud hosting provider
- It prevents anyone on the team from ever fixing bugs after the first day of the project
- It eliminates the need to run automated tests or check the code into version control
= A contractual spec defines exact interfaces and invariants upfront, allowing parallel work by humans or agents without mismatched assumptions.

## A good spec: goal, inputs, outputs, limits, and acceptance tests
A complete specification for an agentic feature or coding task contains five practical sections: the business goal, exact inputs, expected outputs, strict limits (what not to touch or do), and concrete acceptance tests. Including explicit negative constraints, such as which files must not be modified or which libraries are forbidden, stops coding agents from over-engineering or breaking neighbour modules.

For example, a spec for an invoice parser states the goal, shows sample PDF inputs, defines the exact JSON output schema, forbids adding new external packages, and lists five test invoices that must parse with 100 per cent accuracy.

When acceptance tests are written directly in the spec, both the coding agent and the human reviewer know what done looks like.

?? Why should a good specification for a coding agent include explicit limits (non-goals and forbidden changes) alongside the main goal?
+ To stop the agent from modifying unrelated files, adding unwanted dependencies, or over-engineering features outside the scope
- To make the specification document look longer for client billing purposes
- Because language models only read the negative sentences in a prompt and ignore positive ones
- To slow down the network connection between the developer's laptop and the API server
= Coding agents often try to be overly helpful by refactoring unrelated files or installing extra libraries unless the spec explicitly states what is out of bounds.

## Reviewing what the coding agent built against the spec
Reviewing what a coding agent built against the spec is the verification step where a human engineer checks every requirement, boundary, and acceptance test before merging the code. Passing the automated test suite is necessary, but it is never sufficient on its own because an agent might have weakened a test, hardcoded a value, or introduced a subtle security hole.

It is like a building inspector walking through a newly wired house with the original blueprint and a voltage tester, checking inside the fuse box rather than just flipping one light switch in the hall.

As a consultant, you remain fully accountable for every line of AI-generated code deployed into a client's production environment.

?? Why must a human engineer still review the diff and test suite against the spec even when the coding agent reports that all tests pass?
+ The agent may have misunderstood an edge case, introduced a security flaw, or modified the tests themselves to force a passing result
- Coding agents intentionally insert syntax errors on every tenth line of code as a watermark
- Version control systems like Git refuse to commit files unless a human types a 500-word essay
- Automated unit tests only check whether variables are spelled correctly in British English
= Passing tests do not guarantee that the tests themselves are faithful to the spec or that the implementation is free from security, performance, or architectural flaws.

## Writing an agent architecture spec
An agent architecture specification is the master design document that explains how an entire AI system will work end to end before the team builds it. It covers the business problem, user journey, chosen pattern (workflow, single agent, or multi-agent), model choices, retrieval sources, tool permissions, guardrails, evaluation metrics, and operational runbooks.

Think of it as the complete charter for an expedition, showing the route, supplies, radio frequencies, and rescue plan so the client's engineering, security, and legal teams can all sign off together.

Writing this document exposes missing data sources or unapproved tool permissions in week one, when changing the design costs an afternoon rather than a three-month rewrite.

?? What is the primary business value of writing an agent architecture spec before starting implementation?
+ It aligns engineering, security, and business stakeholders early and uncovers missing data, permission risks, or design flaws while changes are still cheap
- It allows the consulting team to skip building any evaluations or guardrails later in the project
- It automatically trains a custom foundation model using the words in the document
- It guarantees that the model provider will never deprecate an API version in the future
= An upfront architecture spec surfaces hidden integration hurdles, security gaps, and misaligned expectations on paper before expensive engineering time is spent.

## Threat modelling and failure analysis
Threat modelling and failure analysis systematically ask two questions of your architecture design: how could a malicious attacker abuse this system, and how could the system fail accidentally under normal use? You walk through every input, retrieval store, model step, and tool call to list potential prompt injections, data leaks, hallucinations, rate-limit crashes, and runaway loops, along with the specific control that mitigates each one.

It is like a bridge engineer calculating both what happens during an accidental fifty-year storm and how to secure the maintenance hatches against deliberate vandalism.

Putting a clear threat and failure table inside your design document gives enterprise security reviewers immediate confidence that you take safety seriously.

?? How do threat modelling and failure analysis complement each other in an agent design document?
+ Threat modelling examines how malicious attackers could exploit the system, while failure analysis examines how components could break or misbehave accidentally
- Threat modelling is done only after a breach occurs, while failure analysis is done only for hardware servers
- Threat modelling measures token cost, while failure analysis measures user interface colour contrast
- Threat modelling applies only to open-weight models, while failure analysis applies only to closed APIs
= A resilient design must account for both adversarial abuse (such as prompt injection and data theft) and non-malicious operational failures (such as API timeouts, hallucinations, and runaway loops).

## Diagrams: components, data flows, and trust boundaries
Architecture diagrams show visually how components connect, which direction data flows at each step, and where trust boundaries sit between untrusted inputs, the language model, and privileged internal systems. Marking trust boundaries with a clear dotted line makes it obvious where untrusted external text enters the pipeline and where deterministic permission checks or human approvals must stand guard.

It is like a castle floor plan that clearly marks the public outer courtyard, the guarded drawbridge, and the locked inner treasury so everyone can see where visitors are stopped and searched.

A single clear diagram showing components, data arrows, and trust boundaries communicates more in five seconds to a client CTO than ten pages of dense prose.

?? Why is drawing explicit trust boundaries on an agent architecture diagram so valuable during a design review?
+ It visually highlights every point where untrusted data or unverified model outputs cross into privileged systems, showing exactly where security controls are needed
- It makes the slide deck look more colourful for the marketing department
- Cloud providers automatically read architecture diagrams to configure firewall rules without code
- Trust boundaries reduce the number of vector dimensions needed in the embedding database
= Marking trust boundaries shows reviewers immediately where untrusted external content enters the system and where deterministic validation or human gates must sit before privileged actions execute.

## Cost and latency estimates before building
Estimating cost and latency on paper before building prevents the painful surprise of launching an agent that works accurately in a demo but is too slow or expensive for real client traffic. You estimate latency by adding up the sequential model calls, average input and output tokens, and tool response times along the critical path, and estimate cost by multiplying expected token volumes and tool fees by daily request counts.

For example, if a multi-agent workflow makes eight sequential frontier-model calls taking four seconds and £0.08 each, a customer waiting 32 seconds on a live phone line or a client processing 100,000 daily tickets at £8,000 a day will reject the design immediately.

Doing this five-minute back-of-the-envelope calculation early tells you whether you need parallel steps, caching, or smaller models from the start.

?? How do you estimate the end-to-end latency of an agentic workflow before writing the code?
+ Sum the expected duration of the sequential model calls and tool executions along the critical path of a typical request
- Multiply the total number of lines in the system prompt by the number of engineers on the team
- Divide the monthly cloud budget by the number of customers in the database
- Check the clock speed of the user's mobile phone processor
= Because sequential steps wait for one another, summing the time to first token, token generation time, and tool execution time across sequential steps reveals whether the workflow fits the user's wait-time budget.

Deep-research and coding agents are the two most mature categories of long-horizon autonomous agents in enterprise use today. A deep-research agent breaks a complex question into sub-queries, searches dozens of internal and web sources, cross-checks facts, and synthesises a cited report, while a coding agent explores a repository, edits multiple files, runs tests, and iterates on compiler errors until the task is complete.

## Durable, resumable long-running tasks
Durable, resumable execution ensures that a long-running agent task that takes minutes, hours, or days can survive server restarts, network blips, rate-limit pauses, or overnight human approval waits without losing its place. Instead of holding the agent's progress only in temporary RAM, a durable runtime saves the state of every completed step and tool result to persistent storage.

It is like playing a long video game that automatically saves your progress at every doorway so that if the power cuts out, you resume right outside the boss room rather than back at level one.

?? Why is durable, checkpointed execution critical for agent tasks that run for thirty minutes or wait for human sign-off?
+ It persists completed steps to disk or a database so the workflow can resume from the last checkpoint after a crash, timeout, or approval pause without starting over
- It makes the language model generate tokens ten times faster than standard API calls
- It eliminates the need to authenticate users before they start a task
- It compresses all output files into encrypted audio recordings
= Storing state durably after each step prevents costly restarts when network errors happen and allows workflows to pause cleanly for hours while waiting for a human to click approve.

## Re-testing your system when a new model arrives
Whenever a model provider releases a new frontier or fast model, or deprecates an older snapshot, you should run your project's automated evaluation and security regression suite against the new candidate before switching production traffic. A newer model frequently lets you simplify complex multi-step chains, drop brittle prompt workarounds, or cut token costs in half, but it can also change formatting habits or verbosity in ways that break downstream parsers.

Think of a racing team bolting a newer engine onto their car: they always run telemetry laps on the test track first to tune the gearbox before entering Sunday's race.

With a good eval suite already in place, testing a brand-new model takes an afternoon rather than a month of guesswork.

?? Why should you run your automated evaluation suite whenever a new model version is released, even if the new model tops public leaderboards?
+ To verify that the new model improves cost, latency, or quality on your specific client tasks without breaking custom formatting, tool calls, or safety guardrails
- Because public leaderboards are written in encrypted code that nobody can read
- Because new models always perform worse than three-year-old models on every task
- Because cloud providers delete your database if you do not run an eval within one hour of a release

## Layers: interface, orchestration, agents, tools and integrations, memory and data, guardrails, evals and observability
A complete enterprise AI system can be understood cleanly through seven distinct architectural layers: the user or API interface, orchestration (routing and workflow state), agents (models, prompts, and reasoning loops), tools and integrations, memory and data (RAG and state stores), guardrails (input/output safety and permissions), and evals and observability running across the whole stack.

Think of a modern office building: the reception lobby is the interface, the lift controller is orchestration, the specialist staff are agents, the phone lines are integrations, the filing room is memory, security turnstiles are guardrails, and CCTV plus building telemetry are observability.

Using this seven-layer checklist in every client discovery workshop guarantees you never design a clever agent while forgetting guardrails, memory isolation, or production monitoring.

?? Why is a layered architecture framework useful when designing an enterprise AI system with a client?
+ It provides a complete checklist of concerns so you design interfaces, orchestration, models, tools, data, guardrails, and observability together without blind spots
- It forces every software project to hire seven separate consulting firms
- It requires seven sequential language model calls for every single user greeting
- It eliminates the need for any database or security controls in the application
= Separating the stack into clear layers ensures critical production requirements like guardrails, observability, and data boundaries are designed upfront rather than bolted on after a failure.

## One decision per layer: build, buy, or skip
For each of the seven layers in your architecture, you make a deliberate business decision with the client: build it custom in-house, buy or adopt an existing platform/open-source tool, or skip the layer entirely if the use case does not need it. A simple internal document summariser might skip complex multi-agent orchestration and long-term conversational memory completely, buy a managed observability tool, and build custom domain prompts and evaluation sets.

It is like opening a bakery where you buy a standard commercial oven and payment terminal off the shelf, skip building a delivery fleet at first, and spend all your creative energy crafting your signature sourdough recipe.

Custom-building commodity plumbing like trace dashboards wastes your client's budget, while outsourcing your client's core domain evaluations gives away their competitive edge.

?? In the "build, buy, or skip" decision across architecture layers, when is "skip" the smartest choice for a layer?
+ When the current use case does not actually need that capability, such as skipping long-term cross-session memory for a stateless one-shot invoice extractor
- When the layer involves security guardrails or evaluation on a high-risk customer-facing agent
- When the engineering team wants to launch to production without any user interface or API
- Whenever a commercial vendor offers a cheap off-the-shelf tool for a required layer
= Skipping unnecessary layers (like multi-agent orchestration or long-term memory when a stateless workflow suffices) keeps the system lean, fast, and easy to maintain.

## Architecture decision records: writing down what you chose and why
An Architecture Decision Record (ADR) is a short, one-page note stored in the project repository that documents a single important technical choice, the context and constraints at the time, the alternatives considered, and the trade-offs accepted. For example, an ADR might record why the team chose a single workflow using a fast mid-tier model and a relational vector index instead of a multi-agent graph with a separate vector database.

It is like a ship's captain logging why they steered south around a storm system so the next watch officer understands the route and knows when to turn back north once the weather clears.

In the fast-moving AI field, ADRs are priceless six months later because they tell future engineers which assumptions have changed when new models or lower prices arrive.

?? Why are Architecture Decision Records (ADRs) especially valuable in fast-moving AI projects?
+ They capture the exact constraints, model limits, and cost trade-offs behind a design choice so future teams know when a newer model or price drop makes it worth revisiting
- They automatically compile English text into GPU assembly code during deployment
- They legally prevent the client from ever upgrading their software in the future
- They replace the need for version control systems like Git
= Because AI model capabilities and prices shift rapidly, recording why a decision was made under specific project constraints lets future engineers spot immediately when an old workaround can be retired.

## Decision ladder: single prompt, workflow, single agent, multi-agent (see B4.1, B9.1)
The architecture decision ladder orders AI patterns from simplest and most predictable to most autonomous and complex: first try a single well-structured prompt, then a deterministic multi-step workflow, then a single tool-using agent, and only at the top rung a multi-agent system. At each rung on the ladder, you climb higher only when evaluation data proves that the simpler rung cannot handle the task's branching or domain breadth.

It is like a doctor starting with rest and physiotherapy before prescribing strong medication, and trying medication before scheduling major surgery.

In consulting engagements, climbing only as high on this ladder as the task truly demands is the single best way to deliver projects on time, within budget, and with high reliability.

?? According to the architecture decision ladder, when should you move up from a deterministic workflow to an autonomous single agent or multi-agent design?
+ Only when the task requires dynamic, input-dependent planning or tool selection that cannot be mapped as a fixed sequence of steps
- Immediately on day one of every project so the architecture diagram looks impressive
- Whenever the client's budget is small and they need the lowest possible token cost
- Whenever the task involves calculating exact payroll taxes from a fixed table
= Each step up the ladder trades predictability, speed, and low cost for flexibility; you should only add autonomous loops or multiple agents when fixed steps cannot handle the variability of the task.

## Matching autonomy to risk and reversibility (see B4.2, B11.2)
Matching autonomy to risk and reversibility means calibrating how much freedom an agent has based on how much damage a mistake would cause and how easily that mistake can be undone. Actions that are low-risk and easily reversible, like creating a draft ticket, tagging an internal note, or running a test in a sandbox, can run with high autonomy, whereas high-risk, irreversible actions, like wiring funds, deleting production tables, or sending legal notices to customers, must be gated by deterministic rules and human approval.

Think of word-processing software: auto-correcting a typo can happen silently because you can press Undo in a second, whereas formatting the entire hard drive asks for explicit confirmation.

You can give a single agent high autonomy on its research and drafting tools while locking its external action tools behind an approval queue.

?? Which combination of action characteristics justifies allowing an AI agent to execute a tool call autonomously without human sign-off?
+ Low business risk and high reversibility, where any mistake is cheap and easy to undo
- High financial impact and complete irreversibility, such as executing an international wire transfer
- External customer-facing legal commitments that cannot be recalled once sent
- Permanent deletion of production customer databases without backups
= Autonomy should be tuned per tool: reversible, low-blast-radius actions can run automatically for speed, while high-impact, irreversible actions require strict guardrails and human approval.

## Scaling up: from one user to many clients
Scaling an AI prototype that works for one user on a laptop into a production service for thousands of users or multiple enterprise clients changes every layer of the architecture. You must introduce per-tenant data isolation, asynchronous job queues to handle traffic spikes without hitting model rate limits, semantic or exact caching, cost budgets per customer, and automated monitoring alerts.

It is like scaling a home kitchen dinner party for four friends into a commercial catering business serving five hundred wedding guests every Saturday without mixing up a single nut-allergy meal.

Many consulting pilots stall before production because the team estimated only the model prompt and forgot the multi-tenant security, rate-limit queueing, and per-client cost metering.

?? What architectural changes are typically required when moving an AI agent from a single-user prototype to a multi-client production service?
+ Enforcing strict tenant data isolation, adding queues and rate-limit management, tracking per-client token budgets, and deploying production observability
- Rewriting all prompts to be ten times longer so the model works harder
- Sharing a single global conversation memory across all competing clients to save database space
- Removing all authentication checks so requests load faster in the browser
= Production multi-tenant scale requires hard tenant isolation in data and memory, resilient queueing against provider rate limits, per-tenant cost controls, and automated observability.

## ERP and MRP system: system of record, calculation code, ask-your-data and exception agents
