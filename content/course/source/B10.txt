## Nodes, edges, and shared state
~m
LangGraph models an agent workflow as a graph made of three building blocks: nodes, edges and shared state. Check the current details for recent API changes.

Shared state is a single typed data record that holds the progress of the run. Nodes are functions that read that state, do one piece of work and write updates back to the state. Edges are the arrows connecting nodes, defining which node runs next.

It is a board game where the board is the graph, the counters and score sheet are the shared state, and each square tells you what action to take next.

This structure turns messy agent logic into an explicit map you can inspect and test.
?? What are the three core building blocks of a LangGraph workflow?
+ Nodes that do work, edges that connect them and a shared state object they read and update
- Tables, rows and foreign keys in a spreadsheet
- HTML tags, CSS rules and browser cookies
- Random prompts with no shared data
= A graph workflow combines processing steps (nodes), transitions (edges) and a single shared state record.
## Cyclical workflows
Traditional data pipelines are directed acyclic graphs (DAGs): data flows strictly forward from start to finish and never loops back.

Agent work is different. An agent writes code, runs a test, sees an error, edits the code and runs the test again. That requires a cycle, an arrow that points back to an earlier step until a check passes. Graph-based agent frameworks are built specifically to support these controlled loops.

It is a chef tasting a sauce, adding salt and tasting again, rather than serving whatever came out on the first stir.

Cycles give agents the ability to retry and self-correct inside a predictable structure.
?? Why do agent workflows often need cycles rather than a strictly one-way pipeline?
+ Agents frequently need to try an action, inspect the result and loop back to revise until a check passes
- Cycles allow the workflow to skip reading the user's input
- One-way pipelines cannot call language models at all
- A cycle guarantees the run uses zero tokens
= Retry, tool-use and revision loops all require returning to an earlier step when the work is not yet complete.
## Why graphs: agent work as steps and decisions you can draw
When agent control logic is buried inside nested `if` statements and prompt instructions, nobody on the team can tell what paths the system might take.

Representing the workflow as a graph forces you to draw every step and every decision point explicitly. You can render the graph as a diagram, show it to a client, and trace exactly which node ran and which branch was taken on any failed run.

It is a London Underground map: you can see every station and every interchange at a glance instead of guessing where the tunnel goes.

If you cannot draw your agent's control flow on a whiteboard, it is probably too tangled to debug in production.
?? What is a practical advantage of modelling an agent workflow as an explicit graph?
+ Every possible step and branch is visible, making the workflow easier to explain, test and debug
- It removes the need to write any functions
- It lets the model invent new database tables at random
- It hides the control flow from developers
= An explicit graph makes the allowed steps and transitions visible both in code and as a diagram.
## Nodes: one step of work (an LLM call, a tool, or plain code)
A node in a graph is just a regular function that takes the current state as input and returns the fields it wants to update.

Crucially, not every node has to call a language model. One node might call an LLM to draft a SQL query. The next node might be ten lines of plain Python that validate the query syntax. The third node might execute the query against Postgres.

It is a relay race where some runners are AI models and others are fast, deterministic code functions handing the baton along.

Mixing plain-code nodes with model nodes keeps the workflow fast, cheap and predictable wherever AI is not needed.
?? What can a node in an agent graph contain?
+ An LLM call, a tool execution or plain deterministic code that reads and updates the state
- Only a frontier language model call and nothing else
- Only user-interface styling rules
- A complete copy of the operating system
= Because a node is simply a function over state, you can freely mix model calls, tool calls and ordinary code steps.
## Edges: what runs next; conditional edges choose a path
Edges control the order of execution between nodes. They come in two kinds: normal edges and conditional edges.

A normal edge is a fixed arrow: when Node A finishes, always go to Node B. A conditional edge is a decision function that inspects the current state and chooses which node to visit next. For example, if `state.error` is present, route to the `fix_query` node; otherwise route to the `summarise_results` node.

It is a railway points switch that checks the signal and directs the train onto platform one or platform two.

Putting routing logic in conditional edges keeps navigation in testable code rather than inside a node's prompt.
?? What is the difference between a normal edge and a conditional edge in a graph?
+ A normal edge always goes to the same next node, while a conditional edge inspects the state to choose the path
- A normal edge costs tokens, while a conditional edge is free
- Conditional edges can only point backwards
- Normal edges delete the shared state
= Conditional edges read the state after a node finishes and branch to different nodes based on what happened.
## Shared state: the single record every node reads and updates
Instead of passing long chains of function arguments from step to step, a graph workflow keeps one shared state object for the run.

When a node finishes, it returns only the fields it changed, such as `{"sql_query": "SELECT ..."}` or appending a new item to `messages`. The graph merges those updates into the shared state before calling the next node.

It is a patient's medical chart on the end of a hospital bed: each nurse or doctor reads the chart, performs their check and writes their entry on the same record.

Having one source of truth makes it easy to inspect the exact state of the run at any step.
?? How do nodes share information in a graph-based workflow?
+ Each node reads what it needs from the single shared state object and returns updates to merge back into it
- Every node emails a spreadsheet to the user
- Nodes guess what earlier nodes did without reading any data
- Each node overwrites the entire database from scratch
= The shared state acts as the single record for the run, updated cleanly after each node finishes.
## Loops need an exit: step limits and stop conditions
Any graph with a cycle can loop forever if the exit condition is never met.

You protect against runaway loops in two places. First, in the conditional edge: track a counter such as `revision_count` in the shared state and route to an exit or fallback node once it reaches three. Second, at the graph runner level: set a hard recursion or step limit (such as 25 total node visits) so the framework stops the run automatically if a bug creates an endless cycle.

It is fitting both a thermostat and a fuse to a heater: one stops it in normal use, and the other cuts the power if the first fails.

Never deploy a cyclical graph without both checks in place.
?? What two safeguards prevent a cyclical agent graph from running forever?
+ A stop condition in the conditional edge (such as a retry counter) and a hard maximum step limit on the graph run
- Asking the model nicely not to loop
- Removing all conditional edges from the graph
- Using a larger font in the system prompt
= Combining an explicit retry counter in state with a framework-level step cap guarantees every loop terminates.

## State-driven transitions between agents
In a multi-agent graph, each specialist agent is simply a node, and transitions between agents are driven by fields in the shared state.

When the `research_agent` node finishes gathering facts, it writes `{"research_complete": true, "findings": [...]}` to the state. The conditional edge reads that flag and routes control to the `writer_agent` node. If `findings` is empty, it routes to `clarify_with_user` instead.

It is an office workflow where moving a ticket's status column from "Research" to "Ready for Drafting" automatically assigns it to the copywriter.

Agents do not need to know how to call each other directly; they only update the state.
?? How does control move from one specialist agent to another in a state-driven graph?
+ The finishing agent updates the shared state, and a conditional edge reads those state fields to pick the next agent
- Each agent opens a raw network socket to the next agent's server
- The user must copy and paste the text between agents manually
- Agents compete to see who responds fastest
= Decoupling agents through shared state lets your graph edges control who runs next based on clear flags and data.
## State machine routing
A finite state machine is a classic engineering pattern: the system is always in one known state (such as `gathering_details`, `awaiting_approval`, `executing` or `done`), and clear rules define which transitions are legal from each state.

Applying state machine routing to agents means an agent in `gathering_details` cannot jump straight to `executing` without passing through `awaiting_approval`. Your code enforces the legal transitions, even if a prompt injection tries to trick the model into skipping ahead.

It is an online checkout that will not let you reach the "Order Confirmed" screen until the "Payment Authorised" step has succeeded.

This makes compliance and safety rules enforceable in code rather than hoped for in prompts.
?? Why is state machine routing valuable for safety and compliance in agent workflows?
+ Code enforces which transitions are legal, so an agent cannot skip required steps like approval even if prompted to
- It allows any step to jump to any other step at random
- It replaces all code checks with a single system prompt
- It hides the current state of the workflow from logs
= Enforcing legal state transitions in code prevents the model from bypassing mandatory checks or approvals.
## The state decides who acts next, not the last speaker
In early chat-based multi-agent setups, the last agent to speak was asked to name the next speaker in prose. Models frequently misspelled agent names, picked the wrong colleague or chatted back and forth politely without doing the work.

In state-driven control, the routing function inspects objective fields in the state: is `sql_validated` true, is `review_status` set to `needs_changes`, is `attempt_count` under the limit? Code then picks the next node deterministically whenever possible.

It is air traffic control assigning the runway from radar data rather than letting pilots vote over the radio on who lands next.

Reserve LLM routing decisions for genuine ambiguity, and use state fields for everything else.
?? Why is routing from state fields more reliable than asking the last agent to name the next speaker in prose?
+ Code can check objective state flags deterministically, avoiding misspelled names or polite loops between agents
- Prose routing is too deterministic and never makes mistakes
- State fields cannot store strings or booleans
- Models refuse to run unless they choose the next speaker
= Deterministic checks on state fields eliminate unnecessary LLM routing errors whenever the next step follows clear rules.
## Keeping state small: only what the next step needs
It is tempting to tip every raw search result, every intermediate draft and every agent's internal scratchpad into the shared state. Within ten steps the state balloons to fifty thousand tokens, slowing every node and muddling the prompts.

Keep the shared state lean. Store distilled outputs, structured fields and references (such as document IDs or file paths) rather than giant raw blobs. Each node should read only the slice of state its job requires.

It is passing a colleague a one-page handover form rather than forwarding your entire email inbox from the past six months.

A small, tidy state keeps every node call fast, cheap and focused.
?? What happens if every agent dumps all of its raw tool outputs and scratchpads into the shared state?
+ The state bloats rapidly, making downstream prompts slow, expensive and harder for models to follow
- Later agents run faster because they have more tokens to read
- API providers stop charging for input tokens once state is large
- The database automatically deletes old tables
= Keeping only distilled results and needed fields in shared state prevents context bloat across the team.
## Typed state: catching bad data between agents
When Agent A passes data to Agent B through shared state, a missing field or a number formatted as a string can cause Agent B to fail halfway through its turn.

Defining your shared state with a strict type schema, such as a Pydantic model or TypedDict in Python or a Zod schema in TypeScript, catches bad data at the boundary. If Node A tries to write an invalid status value or omits a required list, validation fails immediately right at Node A.

It is standard shipping containers that must fit the crane hooks at every port, so a misshapen crate is rejected before the ship sails.

Typed state turns mysterious downstream agent failures into clear, immediate schema errors.
?? How does a typed state schema help in a multi-agent workflow?
+ It validates updates at the moment a node writes them, catching missing or malformed data before the next agent runs
- It lets agents write any data shape they like without checking
- It removes the need for any error handling
- It translates English text into French automatically
= Validating state updates against a schema catches broken handoffs at the source rather than three steps later.
## Checkpoints: pause, resume, and replay a run
A checkpoint saves a snapshot of the shared state to a database after every node completes.

Checkpoints unlock three powerful capabilities for production agents. First, fault tolerance: if a server restarts on step seven of ten, the run resumes from step six instead of starting over. Second, human-in-the-loop: the graph can pause before a sensitive action, wait hours for a manager to click Approve, and resume from the exact saved state. Third, debugging: you can load the checkpoint from step four and replay from there to test a fix.

It is saving your progress in a video game before a hard level so you do not restart from the opening scene.
?? What three capabilities does saving state checkpoints after each node give you?
+ Resuming after crashes, pausing for human approval and replaying from an earlier step to debug
- Free API calls, faster network cables and larger monitors
- Running without a database, skipping authentication and deleting logs
- Training a new model after every turn
= Persisting state at each step lets a workflow pause for hours, recover from failures and be replayed from any node.

## Specialist agents (researcher, writer, editor)
A classic multi-agent pattern divides a complex content or analysis job across three distinct roles: a researcher, a writer and an editor.

The researcher has search and database tools, and its only job is to gather verified facts and source citations. The writer has no search tools; it takes the researcher's notes and turns them into a clear draft that follows the style guide. The editor checks the draft against the source notes and the client rubric.

It is how a newspaper works: reporters gather the facts, feature writers craft the piece and sub-editors check accuracy and house style.

Each prompt stays short and focused on one skill instead of juggling three at once.
?? Why does separating researcher, writer and editor roles often beat a single all-in-one prompt?
+ Each agent focuses on one clear objective with its own tailored prompt and tools, reducing conflicting instructions
- Three agents always cost a third of the tokens of one agent
- The writer can invent facts freely without the editor checking them
- None of the agents need to read the user's request
= Splitting gathering, drafting and checking keeps each prompt focused and lets the editor audit the writer against the researcher's facts.
## Applying single responsibility to teams
In software engineering, the single-responsibility principle says each module should have one clear job and one reason to change. The same rule applies to agent teams.

When one agent is responsible for SQL queries, policy interpretation, customer tone and refund approval, tweaking the prompt to fix a SQL bug often breaks the customer tone. When each agent has a single responsibility, you can improve and test the SQL agent without touching the customer-service writer.

It is keeping the kitchen separate from the front-of-house staff so changing the oven does not muddle the table bookings.

Give each agent one clear job whose output you can test on its own.
?? How does the single-responsibility principle help when maintaining a multi-agent system?
+ You can improve and test one specialist agent's prompt or tools without accidentally breaking unrelated behaviours
- It forces all agents to share a single giant system prompt
- It means the whole team can only answer one question per day
- It removes the need for any evaluation tests
= Narrow, well-bounded responsibilities make individual agents much easier to tune, test and debug in isolation.
## Start from the work, not the org chart: list the tasks first
A common mistake when building a multi-agent system is starting by inventing a grand company org chart: a CEO agent, a VP of Strategy agent, a Marketing Director agent and an Intern agent.

Models do not need middle management. Start instead by listing the concrete tasks required to turn the input into the output, the tools each task needs and the checks between them. Only group tasks into separate agents when they genuinely need different tools, different context or an independent review perspective.

It is designing a workshop around the machines and steps needed to build a chair, not hiring five vice-presidents first.

If two agents have the same tools and run back-to-back on the same context, they should almost certainly be one agent.

## Pipeline: work passes down a fixed line
A pipeline topology arranges agents in a fixed straight line: Agent A finishes and passes its output to Agent B, which passes its output to Agent C.

For example, an RFP response pipeline might run `requirements_extractor` -> `knowledge_base_matcher` -> `draft_writer` -> `compliance_checker`. The order never varies, and no agent needs to decide who speaks next.

It is a car wash tunnel where every car goes through pre-rinse, soap, brushes, wax and dryer in the exact same order.

Pipelines are the easiest multi-agent topology to build, test, time and budget because the path is completely predictable.
?? What makes a pipeline topology the simplest multi-agent structure to manage?
+ Agents run in a fixed, predetermined sequence, so the path, cost and timing are easy to predict and test
- Any agent can call any other agent at random
- It requires a central manager LLM call after every token
- It skips all intermediate steps and runs only the last agent
= When every job follows the same stages, a fixed pipeline avoids routing overhead and makes testing straightforward.
## Supervisor: one agent delegates and collects results
In a supervisor topology, a single central supervisor agent sits at the hub while specialist worker agents sit on the spokes.

Workers never talk directly to each other. The user's request comes to the supervisor. The supervisor calls Worker A, reads the result, decides whether Worker B is needed next, calls Worker B, and finally writes the response to the user.

It is a general practitioner (GP) who refers you to a cardiologist for a scan, reads the specialist report when it comes back and explains the treatment plan to you.

Because every handoff goes through the hub, you have one clear place to log progress, enforce budgets and maintain the overall goal.
?? How do worker agents communicate in a supervisor topology?
+ They do not talk directly to each other; each worker reports back to the central supervisor, which decides the next step
- Every worker broadcasts messages to every other worker continuously
- Workers message the end user directly in separate chat windows
- The supervisor runs once at the start and then shuts down before workers finish
= Routing all delegation and results through a central supervisor keeps control in one place and prevents chaotic cross-talk.
## Hierarchy: supervisors of supervisors for large jobs
When a system grows beyond five or six tools and specialists, a single supervisor starts picking the wrong worker because its prompt is crowded with too many options.

A hierarchical topology solves this by grouping specialists into teams, each with its own team-lead supervisor, underneath a top-level supervisor. For instance, the top supervisor routes between a `Data Team` supervisor and a `Content Team` supervisor, and each team supervisor manages its own three specialists.

It is a large hospital where the clinical director coordinates department heads for surgery, radiology and pharmacy, rather than scheduling every nurse personally.

Only introduce a second layer of supervisors when a single supervisor's routing accuracy measurably drops.
?? When does a hierarchical (supervisor-of-supervisors) topology become useful?
+ When there are too many specialists or tools for a single supervisor to route accurately on its own
- On a simple two-step task with one tool
- When you want to minimise the number of model calls
- When no specialists exist in the system
= Grouping specialists under mid-level supervisors keeps each routing decision limited to a small, clear set of choices.
## Network: agents hand off to each other freely
In a network (or mesh) topology, there is no central boss. Any agent can decide to hand control directly to any other agent in the group.

For example, a `sales_agent` chatting with a customer can transfer directly to the `technical_architect_agent` for a deep integration question, which can then hand off directly to the `pricing_agent` to build a quote.

It is a small workshop where craftspeople pass a job directly across the bench to whoever is needed next without asking a manager first.

Networks cut out the middleman call of a supervisor, but they are the hardest topology to control: two agents can easily ping-pong a task back and forth if their handoff rules overlap.
?? What is the main risk of a network topology where any agent can hand off to any other agent?
+ Agents can bounce a task back and forth in loops if their handoff boundaries are not tightly defined
- It requires too many central manager calls
- Agents are unable to pass any context at all
- It can only run in a fixed straight line
= Without a central coordinator, peer-to-peer handoffs need strict guardrails and loop limits to avoid endless ping-ponging.
## Choosing a topology: predictability vs. flexibility
Choosing a team topology is a trade-off along a spectrum from predictable control to open-ended flexibility.

At the predictable end sits the **pipeline**: fixed steps, lowest overhead, easiest to test, but unable to adapt when a request needs a different order of steps. In the middle sits the **supervisor**: flexible routing across specialists while keeping one hub in charge. At the flexible end sits the **network**: direct peer handoffs, but hardest to bound and debug.

It is transport: a train on rails is predictable, a bus route with a dispatcher adapts to traffic, and taxis go anywhere at a higher cost.

Always start as close to the pipeline end as your problem allows.
?? What is the sensible default rule when choosing a multi-agent topology for a client project?
+ Start with the simplest, most predictable structure (like a pipeline or single supervisor) that fits the problem
- Always start with a free-form peer-to-peer network of ten agents
- Pick whichever topology uses the most API calls
- Avoid pipelines even when the steps are identical every time
= More flexible topologies cost more to run and test, so only move away from a fixed pipeline where runtime routing is genuinely needed.

A handoff is the moment one agent finishes its part of a conversation or workflow and transfers active control to another agent.

In code, a handoff is often implemented as a special tool call, such as `transfer_to_billing_agent()`, or as a state update that changes `active_agent = "billing"`. From the next turn onwards, the new agent's system prompt and tools take over the conversation.

Make handoffs explicit in your logs so you can always see which agent was in charge at every turn.
?? How is a handoff between agents typically triggered in code?

- By restarting the database server
- By changing the font colour in the chat window
= Implementing handoffs as explicit tool calls or state changes makes transfers clean, testable and easy to log.

Put two or more autonomous agents in a conversation without tight rules and they can fail in uniquely comical ways.

Two agents can fall into a **politeness loop** ("Thank you!" / "You're welcome, let me know if you need anything else!" / "Thanks again!"). A generator and an overly strict critic can **argue** for ten rounds as fixing one rule breaks another. Or a supervisor can **stall**, repeatedly calling the same search worker that keeps returning "no results found".

It is two people holding a door for each other in a corridor, both saying "After you" while nobody walks through.

Prevent these with structured outputs instead of chatty prose, state progress checks and hard turn limits.
?? What is a common cause of two agents getting stuck in a loop?
+ Unstructured chat handoffs or conflicting critic rules with no progress check or turn cap
- Setting a strict maximum step count on the workflow
- Using structured JSON fields to signal completion
- Running deterministic code between steps
= Replacing free-form chat between agents with structured state updates and hard iteration limits stops polite or argumentative loops.
## Tracing a failure back to the agent that caused it
When a user reports that the final report contained a wrong figure, a multi-agent system gives you a mystery: did the researcher fetch the wrong document, did the analyst miscalculate the percentage, did the writer misquote the analyst, or did the editor change the number during polishing?

To answer that in two minutes instead of two hours, your tracing system must record a hierarchical span for every agent run, every handoff payload and every tool call under a single `trace_id`.

It is food traceability on a supermarket pack that tells you the exact farm, batch and packing line a box of strawberries came from.

Without end-to-end traces, teams waste days blaming the wrong prompt.
?? What do you need in place to quickly find which agent in a team introduced a wrong fact?
+ End-to-end tracing that records every agent's inputs, tool calls and handoff payloads under one shared trace ID
- A single log line that prints only the final answer shown to the user
- Guessing which agent is usually worst and editing its prompt at random
- Deleting all intermediate state as soon as each node finishes
= Hierarchical traces let you inspect the exact input and output of each agent in the chain to pinpoint where the fact went wrong.
## Evaluating the team and each agent separately
Testing a multi-agent system requires two levels of evaluation: **end-to-end team evals** and **component-level agent evals**.

End-to-end evals test whether the whole system turns a user request into a good final result. Component evals test each agent in isolation with fixed test inputs: given this exact research brief, does the researcher find the right three facts; given these exact facts, does the writer produce an accurate draft?

It is testing a racing car both by timing a full lap of the circuit and by testing the brakes and engine on a workshop rig on their own.

If an end-to-end test fails, component evals tell you which specialist broke.
?? Why do you need both end-to-end team evaluations and isolated per-agent evaluations?
+ End-to-end evals measure overall user outcome, while per-agent evals isolate which specialist or handoff caused a regression
- Per-agent evals replace the need to ever test the whole workflow together
- End-to-end evals cost zero tokens to run
- You cannot pass test inputs to a single agent on its own
= Component evals let you test and tune each specialist quickly and deterministically, while end-to-end evals verify that the handoffs work together.
## A single agent is the baseline to beat
Before you build a five-agent crew, build the best single agent (or simple prompt chain) you can and measure it on your evaluation set.

Modern frontier models have large context windows, strong reasoning and reliable tool calling. A huge proportion of tasks that needed a complex multi-agent setup two years ago are now handled faster, cheaper and more accurately by one well-structured agent or two chained calls with code checks in between.

It is checking whether one skilled tradesperson can finish the job in an afternoon before hiring a general contractor and four subcontractors.

If a multi-agent team does not clearly beat your single-agent baseline on quality, speed or cost, keep the single agent.
?? What should always be your baseline before committing to a complex multi-agent architecture?
+ A single well-prompted agent or simple prompt chain measured on the same evaluation suite
- A team of twenty agents with no tools
- A human typing answers by hand with no AI
- Having no evaluation suite at all
= A single agent or simple chain is cheaper, faster and easier to debug, so a multi-agent design must earn its complexity on the evals.
